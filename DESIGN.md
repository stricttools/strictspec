# strictspec — Design Charter

strictspec is a strict, multi-language schema toolchain for declarative spec files.
A project defines, once, in a TOML schema, what its spec files (JSON/TOML/JSONL) look like;
strictspec generates the code that reads, validates, and version-gates those files — in Python, Go,
and TypeScript — with read-side verdicts, error codes, paths, AND template-rendered message
text kept identical across all four conformance targets by a shared conformance suite
(write-side TOML fidelity is within-backend only). Cross-document validation is portable by
construction: a declarative constraint vocabulary over closed evidence resolvers, executed by
a constraint engine ported to every target and conformance-tested exactly like structural
validation; the genuinely bespoke tail is consumer-native code over generated typed values,
outside strictspec by declaration. Format migrations are declarative op lists, executed by the
strictspec CLI and by tool-generated version-boundary checkpoints — never receiver-side, never
automatic. The CLI is eight commands: gen, check, validate, migrate, export, init, diff,
doc-diff.

Analogy: protobuf for human- and agent-edited config files. Schema in, typed code out in many
languages, with a first-class story for format evolution.

## Motivation (evidence)

A sizing audit across ten declarative projects in this ecosystem found:

- ~7,000–8,000 hand-written lines of duplicated parse/validate/error-report code, plus ~2,200
  lines of hand-maintained format documentation that drifts from the code.
- Systematic policy inconsistency: unknown-key handling ranges from hard-error to warn to
  silent-ignore, sometimes within a single project. Silent ignoring means an agent's typo'd
  field vanishes without an error — the deadliest failure mode for agent-authored files.
- Confirmed cross-language drift: two implementations of the same format accept *different
  documents* (tunebox Go accepts integral floats Python rejects), report different first
  errors, and share zero identical error strings — with no conformance tests guarding any of it.
- Format versioning is nearly absent despite demonstrated rename pain handled by hand-rolled
  compat shims.
- Two projects independently began building this tool in-house (a private sprite tool's schema-to-code
  generator; incantino's schema notation + unwired codegen) and both stalled on incompleteness.

Roughly 70% of the initial build already exists in the ecosystem as disconnected fragments
(see Donor inventory below). Honesty note on the line-count claim: the eliminated lines are
*structural* parse/validate/error code plus — with the declarative cross-document constraint
vocabulary (decision 23) — most cross-file validation logic (references, coverage,
uniqueness). The genuinely bespoke tail (and non-validation analysis like pgdesign's
normal-form work) remains consumer code, out of scope by declaration.

## Architecture (directory map)

## The confidential-term list (implementation decisions)

The `confidential` package of the Go module reads the owner's confidential-term list and the resolutions of its hits. These are implementation decisions made while building it, not owner rulings:

- **Where the list is.** At the path the family's settings file names (see "The confidential-term list's location" below), with the age identity at `~/.age-key.txt`. `LocationFromSettings` takes any settings file and home, so tests and callers never depend on the real ones.
- **Decryption.** In memory with `filippo.io/age`, never by running the `age` program and never through a file: the package calls no `os` function that writes (a test guards it).
- **Format.** `format_version = 1` and `[[terms]]` tables; each entry has one and only one of `term` and `pattern`, an `added` date, a one-line `reason`, and `scope = "everywhere"` or `{ except = [...] }`. Every malformed entry is reported at once; a missing file is a list with no terms, which every caller states.
- **Matching.** A literal matches as a substring ignoring case, inside longer words too: a match is judged hit by hit by the agent, never filtered by the matcher. A pattern is a Go regular expression compiled with `(?i)`; one that matches the empty string is refused.
- **Scope.** An `except` entry names repositories by their directory's name or their `origin` remote's last path segment, the names `RepositoryNames` gives.
- **Hit ids.** 16 hexadecimal digits of the SHA-256 of the entry, the lowered matched text, and up to six lowered words after it on its line. Words before the match are left out so the same phrase keeps its id where a rendering puts other text before it (a JSON changelog line, a Markdown list item, a Release body). Ids name no confidential text.
- **Resolutions.** `.strictmetadata/confidential-hits/resolutions.toml`, owned by strictspec (`manifest.toml` names it) because more than one tool reads it; a resolution is a false positive (certainty 70 to 100) or an approval (no certainty), with a one-line reason and the day. A reason carrying a term is refused, and the location is recorded redacted, since the file is committed.

## The unreleased lifecycle status

Owner ruling: a releasable that has never been released is `unreleased`, and its releases are refused. The status is derived, never recorded: a subject with no lifecycle period in effect is active when its release record holds a release and unreleased when it does not. An active lifecycle period, recorded deliberately (rlsbl's `transition lifecycle`), is what allows a first release. A released subject keeps releasing as before. The recorded statuses stay `active`, `non-releasing` (see the next section), and `retired`.

Implementation decisions made while building it, not owner rulings:

- **The schema is unchanged.** `unreleased` is a `Status` constant (`StatusUnreleased`) for callers to compare against, and the built-in schema's status enum still refuses it, so no record can hold an unreleased period.
- **The release record is the caller's.** The lifecycle record does not know what was released, so `StatusOn` and `ReleaseAllowed` take `released`, whether the subject's release record holds a release. A member's caller passes its releasable's.
- **The refusal names no tool.** `ReleaseAllowed`'s fix says to open an active lifecycle period; the tool refusing the release names its own command for it.

## The non-releasing lifecycle status

Owner ruling: the lifecycle status that refuses a subject's releases is named `non-releasing`; its earlier name, `on-hold`, is gone, with no compatibility for it. A record holding `on-hold` is refused like any status the schema does not list, No record held `on-hold` when the rename was made, so no migration was written.

## The confidential-term list's location

Owner ruling: the list's location comes from a family setting in the user's configuration, not from a path written into public code. A missing setting is an error naming what to set; a missing list file at the path the setting names still means no terms.

Implementation decisions made while building it, not owner rulings:

- **The settings file.** `stricttools/config.toml` under the user's configuration directory (`os.UserConfigDir`: `$XDG_CONFIG_HOME`, else `~/.config`), holding `format_version = 1` and `confidential_term_list = "<absolute path>"`. It is the family's file, not one tool's, so every tool reading the list reads the same setting.
- **Strictness.** A missing file, a missing setting, another format version, an unknown key, and a path that is not absolute (`~` included) are each refused, naming the file and what to write; nothing is filled in.
- **The identity is unchanged.** The age identity stays `~/.age-key.txt` under the home directory; only the list's location moved to the setting.

## The declarations engine

The `declarations` package of the Go module is the shared engine with which a tool keeps declarative TOML files of a project's remote resources in the project's repository, verifies live state against them, imports live state into them, and applies them. Its first consumer is a private tool managing a one-person web infrastructure.

Owner rulings:

- Declarations live in each project's repository, committed, under `.strictmetadata/<directory>/<resource-type>/<name>.toml`: one TOML file per resource, grouped by resource type. The directory's `manifest.toml` names the tool that owns it (the family's manifest convention: one key, `owner`). The tool finds a project's declarations by walking up from the working directory to the project's `.strictmetadata/`, and refuses otherwise: no registry, no scanning.
- Resources belonging to no project are declared in a dedicated private repository, the account repository, whose path is a setting of the tool. It also lists every claim: verify there checks that every live account-level resource is declared there, assigned to one and only one project, or listed unmanaged; verify in a project checks that the project declares only what is assigned to it.
- The schemas and the engine live in strictspec; each tool supplies only its resource types and their live readers and writers. strictspec is not released for this; the tools use it through `go.work`.
- No state file: declarations plus live reads, matched by natural keys. Undeclared live resources are differences unless listed in a required `unmanaged` list, each entry with a reason; declaring and listing the same resource is refused.
- References are typed and point only at provider-assigned values. Records another service dictates are derived from the declaration that causes them, and declaring one by hand is a hard error naming its source. Every field has one owning file. Apply refuses a reference whose value does not exist yet and that no earlier step of the same apply creates.
- DNS record comments are declared (required) and compared.
- verify exits 0 when matching, 2 when differences are found, and 1 on a failure; its JSON carries the same result and the diff. import writes a new file from live state, refusing an existing file. apply is consequential, previews under `--dry-run`, refuses when live state changed since, and refuses when the declaration directory has uncommitted changes.
- The dry run comes first, for every apply: the identifier apply requires comes from the apply's own dry run, not from verify. The dry run prints every write apply would make, in execution order, each deletion spelled out with what it deletes, and ends with the identifier; the real apply accepts only that identifier and refuses if the declarations or live state changed since. verify keeps its report and exit codes but prints no identifier apply accepts.
- One apply runs everything: apply resolves values created earlier in the same run (a new zone's ID, a new server's IPv4) and continues, so a declared reference to such a value is planned, not left unresolved for a later round; the dry run lists every step with placeholders such as `<id of new cloudflare-zone example.org>`. One dry run shows the whole change.
- Undeclared live resources are differences, so apply run in the account repository deletes each `unclaimed` resource (a resource-level delete). In a project apply never deletes a top-level resource: removing its file stops managing it, and the account repository's verify then reports it `unclaimed`. Each resource type's writer supports a resource-level delete.
- The concept is a resource type (`ResourceType`, `resource_type`), named so in code, file formats, flags, and messages, never with another word.

Implementation decisions of the design the engine was built from, not owner rulings:

- **Schemas.** Built-in strictspec schemas in `go/declarations/schemas/`, embedded, Go only (the paused Python and TypeScript built-in generators do not mirror them): `declaration-manifest`, `declaration-project` (`name` matching `^[a-z0-9][a-z0-9-]*$`, the name claims use), `declaration-claims` (`[[claim]]` with `resource_type`, `name`, and one of `project` and `creator`, and `[[unmanaged]]` with `resource_type`, `name`, and `reason`, both arrays required), `declaration-report` (JSON), and the type definitions `declarations.types.toml`, which every resource type's schema imports for its required `unmanaged` array. The engine adds that file to a resource type's schema files.
- **Unmanaged entries.** `{ collection, match, reason }`; `match` holds at least one key, each a field of the collection, and its value is an `opaque` site with the consumer check `declarations.match-value`, which the engine runs at load, refusing anything but a string, an integer, or a boolean. A resource type field accepting two scalar forms uses the same pattern, its consumer check run by the resource type's Decode. An entry matching a declared child, or children a slot covers, is refused at load.
- **Claims.** A resource listed more than once across claims and unmanaged entries is refused naming each place; in the account repository, a claim or unmanaged entry naming a resource the account repository declares is refused at Compare; a `claims.toml` outside the account repository is refused at Compare. `LoadClaims(tool, accountRoot)` returns claims carrying the account root, and Compare recognizes the account repository by comparing it with the project's root, both paths with every symlink resolved; a path that does not resolve is an error. In the account repository Compare lists every live resource of every resource type and reports `unclaimed` for each one neither declared there, claimed, nor unmanaged (an unmanaged one is reported without collection and key); in a project it reports `misclaimed` for each declared resource not claimed for the project's name. A claim naming `creator` instead of `project` assigns a resource a command created to that command, which owns it and nothing declares (a snapshot a backup command takes): the creator adds the claim when it creates the resource and removes it when it deletes it, through `ClaimCreated` and `UnclaimCreated`, which take the bytes of `claims.toml` as the tool holds them (read under the tool's lock, or as its dry run left them after an earlier recorded edit) and return the new bytes edited in place (comments and layout kept, through go-toml-edit) for the tool to write, change nothing when the claim is already there or already gone, and refuse a resource the file assigns otherwise or lists unmanaged. `RenameClaim` returns `claims.toml` with a claim or unmanaged entry renamed, the same way, for a command renaming a live resource. `CreatorClaim` tells a creator, before it deletes a resource, whether the bytes claim it for that creator (true) or list it nowhere (false), and refuses a resource claimed for another owner or listed unmanaged, so a creator never deletes what the claims assign elsewhere. In the account repository a creator's claim naming a resource that is not live (the resource type's list read, and the name absent from it) is a `stale-claim` difference, its `source` `claims.toml`, never silently ignored; apply removes it with an unclaim change (`ActionUnclaim`, carrying the claim as `Change.Claim`) after every other change, which the tool's writer makes by editing `claims.toml`, and the report recomputed after applying no longer holds the claim. A project's claim of a resource that is not live is no difference: the project's apply creates it, so the claim legitimately comes first. A resource type implementing `Owning` names, for a live resource, the live resource owning it (the addresses a provider creates with a server): in the account repository such a resource is never unclaimed; it stays with an owner that is declared, claimed, or unmanaged, and goes with an unclaimed owner, listed in the owner's resource-level delete as `Change.Owned`, never deleted on its own. A resource-level delete carries the live resource as read, so a tool's dry run can spell out what goes. A writer implementing `UsageReader` names the live resources using a resource: `PlanApply` then deletes each resource after every resource the same plan deletes that uses it (a Worker binding a bucket before the bucket), whatever their stages and names, and refuses resources the plan deletes that use each other. `ListImportable(set, account, live, claims, types)` lists the live resources of the named types no declaration covers (declared neither in the project nor in the account repository, neither claimed nor listed unmanaged, owned by no live resource), for a tool's listing of what its import could declare. A `Slot` naming resource types in `YieldsTo` gives way to a slot of a declared resource of one of them covering the same field or child: the yielding slot is dropped at load (its derived value ignored) instead of both being refused as deriving the same thing, so one fixed owner rule decides which file owns a record two services would derive (a domain's DMARC record, which a mail host's declaration owns over a sending service's). A `Descriptor.Companions` entry keeps a compared field's declared value in a file beside the declaration, `<name><suffix>`, which the declaration names under its own key (an HTML body): `Load` reads it into the field, counts its hash in the plan's identifier, refuses a declaration naming another file or a missing one, and refuses a non-declaration file no declaration names; `RenderImport` writes the naming key in the field's place, and `RenderImportCompanions` the file.
- **The tool's side.** `Tool{Name, Command, Directory, InitCommand, DryRunCommand, ResourceTypes}`; `Name` is the owner its manifests name, and `Command` the program its users run, which the engine's messages name (it may differ from the owner name); a refusal naming the init command appends `--project <name>` to `InitCommand`. A `ResourceType` gives its name, schema, and `Descriptor` (compared fields and collections in rendering order, stage, exposed values, create-only fields, derivable fields), decodes a schema-valid document (the engine parses `unmanaged` and sets `File`), and gives its slots (what it causes in another declared resource, without live reads) and their derived values (which may read live state; a value that does not exist yet is unresolved). Derivable fields are a subset of the fields; create-only fields are top-level and are not fields; a child's create-only field is any item field that is neither key nor compared field; a field slot names only a derivable field of its target. The tool also supplies a `LiveReader`, a `Writer` executing one `Change` at a time and saying, without writing, why it cannot make a change (`Refuse`, given the change and the whole plan), and a `Git` running `git status` for the engine.
- **Model.** `Resource`, `Item`, and `Value` (canonical JSON data or a `Reference`). A reference is written `{ <resource type with - as _> = "<name>", value = "<exposed value>" }`; whether a field accepts one is the resource type's schema's decision, and Decode binds it with `ParseReference`.
- **Load.** Refuses an unknown resource type directory, a file not ending in `.toml`, and anything at the top other than `manifest.toml`, `project.toml`, `claims.toml`, and resource type directories; reports every diagnostic of every file in one error; then checks references (declared, exposing the value), slots (the target declared, else naming the file to write), hand declarations and overlapping slots (the compatible-matcher test: equal exact values, or prefixes one of which extends the other), and derivable fields (declared or derived, never both).
- **Compare.** Differences are `missing`, `unexpected`, `changed`, `unresolved`, `unclaimed`, `misclaimed`, and `stale-claim`, sorted by resource type, name, collection, key, and field; `collection`, `key`, `field`, `declared`, and `live` appear only where they apply, and `source` names the declaration file the expected value comes from, or the file that causes it. A missing resource gives one resource-level `missing` (its top-level fields as `declared`) plus one per child; a missing or unexpected child gives its non-key fields as `declared` or `live`. An unresolved derivation gives one `unresolved` difference for its slot and leaves the live children it covers alone; a pending one (below) gives one `missing` difference for its slot, its reason as `declared`, and leaves them alone too. Live reads that fail are listed as unreadable; `Report.ExitCode()` is 1 when anything is unreadable, else 2 with differences, else 0.
- **The plan identifier.** The lowercase hex SHA-256 of the canonical JSON (sorted keys, no insignificant whitespace) of every declaration file's hash, every live resource read (reads made by derivations included, exposed values excluded, sorted by resource type, then name), and the differences: an edited declaration or a change in the live state read changes it.
- **Apply.** `PlanApply(set, live, claims, writer, git)` makes the plan of an apply (`Plan`: the report, the changes in execution order, and the identifier), refusing, in order: an uncommitted or untracked file in the declaration directory, a misclaimed resource, an unreadable resource, and a change the writer refuses (`Writer.Refuse`, asked of every change, each refusal named), so a change the writer cannot make is refused by the dry run and before the first write, never partway through an apply; a tool's dry run prints it. `Plan.Accept(id)` refuses an identifier that is not the plan's, and `Plan.Execute()` runs it through the plan's writer; `Apply(set, live, claims, writer, git, id)` is the three in turn, and a tool with refusals of its own runs them between planning and executing. The refusals name the tool's dry run, `Tool.DryRunCommand`. Apply executes creates and updates in ascending stage and deletes in descending stage, within one resource the resource-level change before its children, never passing an unresolved or misclaimed difference to the writer; each `unclaimed` difference, which only the account repository reports, executes as a resource-level delete among the deletes; it returns the report recomputed after applying.
- **Import.** `RenderImport` renders a new file from a live resource: a header saying it was imported and must be reviewed, `format_version = 1`, the descriptor's fields in order, children sorted by key, and `unmanaged = []`, leaving out create-only fields and what a slot of a declared resource covers. The tool refuses an existing file before reading anything, and writes the bytes. `LoadForImport(tool, project, resourceType, name)` is `Load` with one relaxation, scoped to the one resource being imported: a slot whose target is that resource and is not declared yet is not refused, so `RenderImport` leaves out what the slot covers; every other refusal stays.
- **No writes.** The engine writes no file and starts no process: `Init` and `RenderImport` return bytes, and git runs through the tool's `Git` (a test guards it).

Decisions made while building it, not stated by that design:

- **The manifest's format version.** `manifest.toml` holds only `owner`; the engine supplies `format_version = 1` when it validates the file and refuses a file writing it, as selfdoc's directory manifest does.
- **A directory without its manifest.** `FindProject` refuses a declaration directory that exists without `manifest.toml`, naming the init command, never reading it as declaring nothing. `Init` refuses only when `manifest.toml` exists: for a directory holding declarations but no manifest it returns the files the directory lacks, keeping a `project.toml` naming the same project and refusing one naming another.
- **Paths.** `FindRoot` returns an absolute path; `Init` and `LoadClaims` refuse a root that is not absolute; `Init` keys its bytes by absolute path. A resource's `File` is `<resource type>/<name>.toml` relative to the declaration directory, and a report's `source` is `<resource type>/<name>`. Decode's name must equal the file's stem: a file named otherwise is refused naming the file to rename it to.
- **Failures.** A failed listing is unreadable without a name. A failed derivation is reported unreadable under the resource causing it, and its slots' fields and children are left alone: not compared. A failed exposed-value read is reported under the referenced resource, and the resource referring to it is not compared. Within one comparison every read and exposed value is cached, so a resource a derivation reads reads the same. What a tool gets wrong (an inconsistent descriptor, a slot or derivation outside its target's descriptor, a non-canonical live value) is an error, not a report entry; a live resource may carry fields its descriptor does not compare.
- **One expected child per key.** A slot matches key fields only: a slot matching another field is a bug in the tool, refused at load naming the slot's source. So a hand-declared child sharing a derived child's key is one the slot covers (refused at load), and two slots no child matches both of never derive one key. Keys equal only once references resolve are refused at Compare, which names both sources of the two expected children.
- **Unresolved values.** A missing resource whose top-level value waits on an unresolved value is unresolved as a whole, its children included. An unresolved derivation's `declared` is its reason; an unresolved reference's is the reference as written.
- **Pending values.** A reference to a declared resource that is not live (apply creates it) resolves to a `Pending`, not to an unresolved value; so does a derived field whose derivation is unresolved while its source is not live, and an unresolved collection slot whose source or target is not live becomes a `Deferred` change. A difference holding one is `missing` or `changed`, and the report and the plan identifier show each by its placeholder (`<ipv4 of new <type> <name>>`, `<<field> <type> <name> derives>`). `PlanApply` moves each change after the creations its pending values, or its deferred children, wait on (a child or field of a resource the plan creates also waits on that creation), keeping the stage order otherwise, and refuses a change waiting on a creation the plan does not make and changes waiting on each other. A deferred change is not given to `Writer.Refuse` at planning; its `Covered` lists the live children its slot covers. `Execute` reads each pending value through the tool's live reader once its creations ran (a derived one by running the derivation again), leaves out of a change's expected resource what waits on a creation that has not run yet, and expands a deferred change into the creates, updates, and deletes making the slot's live children match the derivation, asking `Writer.Refuse` of each; a value still missing after its creations stops the apply. `Change.WithPlaceholders` and `Placeholders` give a dry run the plan's values with placeholders in place of pending ones.
- **The report.** `matching` is true when there is no difference and nothing unreadable. Report values (`key`, `declared`, `live`) are unchecked opaque sites of the report schema. Differences tied on the sorting fields are ordered by status, then their values and source. An `unexpected` child's `source` is its resource's file, or the cause's file when a slot covers it; an `unclaimed` difference has none.
- **Apply's order and failure.** Every create and update runs before every delete. A change carries the expected resource without its unresolved values (its pending ones resolved by Execute, or left out while their creation has not run): a live child whose key is resolved carries the live values of its unresolved fields, so a writer never writes an unresolved value, and the children no change names (unmanaged, covered by an unresolved or failed derivation, or unresolved) are not in it; a delete carries the live child. A writer error stops apply at once, naming the change and how many changes ran before it.
- **A fallback key.** A collection may name a `FallbackKey`, compared fields identifying a child that holds none of the collection's `Key` fields (a CORS rule a provider keeps without an id, identified by its origins). A child holds every key field or none of them; the key a difference reports, the duplicate check, and the matching of declared with live children use the fields identifying each child, and import renders a child without the key fields it does not hold.
- **Children in the order of their collections.** Within one resource, apply runs the resource-level change first, then the creates and updates of its children in the order of the resource type's `Collections`, and its child deletes in the reverse order, so a child naming another of the same resource (a forwarding naming its mailbox) is created after it and deleted before it. Across resources the order stays by stage, then resource type and name.
- **A resource-level delete.** It carries a resource holding only its type and name: nothing declares an unclaimed resource, and Compare does not read it, so the writer deletes by name. Deletes of one stage keep the report's order (resource type, name, then collection).
- **The import set.** A set `LoadForImport` returned serves `RenderImport` only: `Compare` and `Apply` refuse it, since its slots may target an undeclared resource. `LoadForImport` refuses a resource type the tool does not supply.
- **Import.** Empty collections are written `<collection> = []` and `unmanaged = []` precedes the `[[<collection>]]` tables, since TOML requires top-level keys before tables. The rendered file is not validated against the schema: a create-only field the schema requires is the reviewer's to add.
