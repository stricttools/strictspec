# go/ — The Toolchain and the Go Releasable

One Go module (`github.com/smm-h/strictspec/go`, with `go.mod` living in this directory): the
toolchain binary (`cmd/strictspec`) plus the runtime subpackage generated Go code imports.
Consumers compile only the runtime. One version, one tag, one release. The MODULE IS THE
BINARY — Go consumers `go install` it directly; there is no separate binary package for Go.
rlsbl emits `go/vX.Y.Z` companion tags alongside the package tag (the strictcli-proven pattern;
decision 10 in the root charter). Non-Go consumers never touch a wrapper package either: the
former `-bin` wrappers are eliminated (decision 31). The published PyPI and npm `strictspec`
packages carry a CLI stub that lazy-downloads the exact-version Go binary from the GitHub
Release — with SHA-256 checksum verification — on FIRST CLI INVOCATION (npm: on first run,
never at postinstall, so library-only installs do zero network). The shims are built on rlsbl's
first-party "launcher" artifact mechanism (checksum-verifying templates). goreleaser
cross-compiled per-OS/arch archives on the GitHub Release are the single binary source of truth.
The CLI is built on strictcli (Go): flag conventions enforced at registration, schema dump
integrated — strictspec does not hand-roll a CLI layer.

## The consumer manifest: strictspec.toml

Generation is FILE-DRIVEN. Each consumer commits a `strictspec.toml` declaring: schema files,
targets per schema (python/go/ts + output paths + package/module names), migration locations,
and — where the consumer has them — STORES and CHANNELS for boundary-checkpoint generation
(see spec/, the version-boundary invariant). `gen` and `check` take the manifest as their
single input. The manifest is itself a document of a toolchain-shipped built-in schema — it
carries a `format_version`, is gated exactly like any document, and is migrated by
`strictspec migrate` when the manifest format evolves. The manifest also mandates
`.gitattributes` LF rules for generated paths (byte-compare dies under autocrlf).

## The CLI (strictcli-based)

Every command declares its effect classification. `gen`, `init`, `export` and `migrate` are
`mutating` and route every disk mutation through the framework's effects handle, so the
framework-owned `--dry-run` is available on all four and records what would happen instead of
performing it; `validate`, `check`, `diff` and `doc-diff` are `read_only`. A mutating command
may declare no value default (a value the framework picked is a value the framework writes),
so `gen --manifest`, `init --manifest`, `export --output` and `migrate --migrations` are
declared optional and name their fallback in their own help text. Absence is delivered as
absence throughout: no flag reads an empty string as "not supplied".

- `strictspec gen` — generate from the manifest. Output files land chmod 444 (selfdoc
  convention); gen chmods before overwrite. Every generated file carries the ecosystem's
  generated-file and lint-suppression markers (`// Code generated by strictspec. DO NOT EDIT.`,
  `# ruff: noqa`, `/* eslint-disable */`); gen maintains repo-level ignore entries (prettier)
  for the manifest-declared generated paths. Hard error when a TS target is declared for a
  schema lacking `safe_integers = true`. Where the manifest declares stores/channels, gen emits
  the ingest write-doors and negotiation/egress wrappers.
- `strictspec check` — drift gate: regenerate from the manifest to temp, byte-compare against
  the toolchain's OWN canonical emitter output. No external formatters exist anywhere — the
  emitters are the formatting authority. Hard error on drift or on a generator-version
  mismatch it cannot reproduce; hard error on runtime/codegen pairing mismatch. Also prints
  the complete blind-spot inventory: unchecked opaque leaves (path + mandatory reason) and
  consumer-check declarations (path + check name).
- `strictspec validate` — interpreter-backed; REQUIRES `--structural-only` or
  `--with-domain-checks`; no default. The two modes are a member-spelled selector, so exactly
  one election is enforced by the declaration rather than by a guard in the handler. The CLI
  hosts domain checks natively: the constraint engine (the cross-document vocabulary) plus the
  toolchain's evidence resolvers run in-process. `--collection` and `--collection-root` live
  INSIDE the `--with-domain-checks` scope — passing either under `--structural-only` is a parse
  error naming both sides, not a silently ignored flag. A resolver the current environment
  cannot satisfy is a hard error naming the resolver — never a skip.
- `strictspec migrate` — execute declarative migrations (documents, JSONL per-line, schema
  files, and the manifest itself); explicit in-memory migration for immutable archives (read
  old bytes, migrate in memory, never write — distinct from the banned silent
  auto-migrate-on-read). Schema files are
  documents of the meta-schema and migrate exactly like any other document, driven by
  declarative meta-migrations shipped INSIDE the toolchain (one set per schema-language version
  bump). All-or-nothing per run: every file transforms and revalidates to temp first; only
  after ALL succeed does the rename sweep run; any failure anywhere = zero changes on disk.
  `--dry-run` renders a per-file structured diff of what the migration would change, zero disk
  writes.
- `strictspec export` — JSON Schema (per the lossiness table) + STRUCTURED SCHEMA METADATA for
  selfdoc rendering. strictspec generates no docs pages (decision 27); selfdoc owns rendering.
- `strictspec init` — write a commented `strictspec.toml` skeleton plus the mandated
  `.gitattributes` LF rules; hard error if a manifest already exists.
- `strictspec diff` — the EMPIRICAL accepted-set engine (spec/, "Accepted-set semantics"; the
  proof-carrying analyzer is unbundled into a separate future project, decision 25). Requires
  a schema at two format versions, the migration between them, and `--corpus <glob>`:
  flip-scan (every corpus flip reported with the document and its killing diagnostics),
  same-version flip-scan (the corpus replayed against the old and new schema at the SAME
  format_version — a document flipping valid→invalid is an un-bumped narrowing, a hard error),
  migrate-round-trip (soundness/completeness against the corpus, counterexamples are real
  documents), down-taxonomy verification. Output: the CERTIFICATE (spec-pinned JSON; evidence
  grades `violated` / `corpus-supported`, the `proven` grade reserved for the future analyzer)
  consumed by rlsbl's format_version deploy gate + a human rendering. `violated` blocks the
  gate; a consumer with no corpus discharges via a committed adjudication file (a
  strictspec-schema'd TOML document, validated like any other).
- `strictspec doc-diff` — schema-aware document-to-document semantic diff: per-path typed
  delta, array moves keyed by declared unique-by. Pinned output shape.

## Toolchain components

- Document model: TAGGED, LEXEME-RETAINING values over go-toml-edit (TOML) and an
  ORDERED-JSON decoder (token walk over encoding/json in UseNumber mode; lexeme
  classification per the primitives appendix; duplicate keys = hard error; int64 overflow,
  float64 overflow, and number-scalar unrepresentable lexemes = hard errors). Ordered semantic
  maps bind to `[]KV`. Datetime scalars per appendix item 11 (TOML natives bind directly; JSON
  binds RFC 3339 strings; kind mismatches are canonical hard errors). NOTE (2026-07-27): "bind
  directly" does NOT mean a parsed `time.Time` — `date`/`time`/`datetime` fields bind the RETAINED
  LEXEME as a Go `string` (the generated frozen-struct field type is `string`; see
  `internal/emit` goType). Binding to `time.Time` would normalize on read (e.g. rewrite a `+00:00`
  offset to `Z` and drop written precision), violating the lexeme-retention invariant (item 11:
  lexemes are retained, no normalization on read; precision preserved as written). Validating a
  TOML-syntax
  document against a schema in which a nullable union is reachable = hard error (also rejected
  at the meta-schema level where document syntax is known). JSONL: LF-only, streamed
  line-by-line so memory is bounded by the largest line, all-errors-in-one-pass per line with
  byte-offset positions, O_APPEND single-writer appends, temp+rename rewrites. Write side
  implements the canonical-serialization appendix: untouched values serialize byte-identically
  from retained lexemes; constructed values render per the pinned table (float values always
  get float lexemes — `float64(5)` writes `5.0`); the write path REFUSES non-current
  format_version serialization (producer-current-only).
- Internal interpreter: full language; validates schemas against the meta-schema; powers
  `strictspec validate`; FOURTH CONFORMANCE TARGET.
- Constraint engine: the reference implementation of the cross-document constraint vocabulary
  evaluator and the evidence-resolver vocabulary (spec/, "Domain checks"; the decision
  language is removed — the bespoke tail is consumer-native code, decision 23). Resolvers
  return data, never verdicts; resolver parity and constraint-verdict identity are conformance
  categories. The Python, TS, and generated-Go runtimes carry ports of the evaluator;
  resolvers are implemented per environment and hard-error where unavailable.
- Migration engine: migrable's code absorbed (migrable is retired), minus CEL, extended to the
  full document model. 13-op closed set with the admission criterion, per-op collision
  semantics, and the down/partial/irreversible taxonomy per spec/. Migration output
  revalidates by construction (lexeme-preserving writes). Also powers the generated boundary
  checkpoints: ingest write-doors and egress wrappers call into this engine (in-process for
  Go consumers; via the packaged CLI for Python/TS server environments; never in browsers).
- Diff engine (EMPIRICAL — the formal analyzer is unbundled, decision 25): corpus flip-scan
  (cross-version and same-version narrowing detection) and migrate-round-trip executors,
  down-taxonomy verification, certificate emission in the spec-pinned format (evidence grades
  `violated` / `corpus-supported`; the `proven` grade with proof objects belongs to the future
  analyzer, which emits the same certificate format). Toolchain-only; golden-output conformance.
- Generator: three emitters from a SHARED EMITTER IR (constructs, cross-field AND
  cross-document constraint forms implemented once, rendered per language). Emits per the
  Generated API Contract: two entry points (raw bytes; tagged values), immutable typed shells,
  generated `with_*` copy helpers, partial-subtree binding, version gate first (structured
  remediation payload), boundary checkpoints where declared. Python target: frozen dataclasses
  + generated checks. Output formatting is the emitters' own canonical, deterministic style —
  pinned by the canonical-emission rules, no external formatters. Deterministic output; every
  file embeds generator version, schema name + format_version, regeneration command,
  generated-by header, MIT/unencumbered notice, and lint-suppression markers.

## Runtime subpackage (what generated Go code imports)

- Diagnostics: pgdesign's pkg/diagnostic generalized (Path instead of Table/Column; NO
  severity field — every diagnostic is an error), terminal + JSON renderers emitting from the
  spec-pinned message templates, canonical value rendering and did-you-mean per appendix items
  5 and 7 (cross-target normative, conformance-asserted), the constructor for
  consumer-prefixed codes (used by consumer-native checks downstream of validation).
- Node coercers (pgdesign lift) extended per scalar rules (number scalar with
  unrepresentable-lexeme rejection; datetime kinds; integral-float, bool-not-int, non-finite
  guards).
- Document loading: ordered lexeme-retaining JSON, TOML, JSONL; the `[]KV` ordered map type;
  tagged value types (the second entry point's input).
- The inline version-gate helper (three-message pattern + structured remediation payload).
- The constraint engine (cross-document vocabulary evaluator) and the Go implementations of
  the evidence resolvers.

Version pairing: generated code and runtime from the SAME release — exact match, hard error.
Dev builds carry a dev version string that pairs only with itself (conformance regenerates
constantly; released and dev artifacts never cross-pair). Under the ecosystem's always-latest
dependency rule this hard error is the INTENDED surfacing of skew; remediation is
regeneration, never pinning.

## Invariants

- No lenient modes. Loading and validation are inseparable; no "parse without validating"
  public entry point.
- Unknown keys are ALWAYS a canonical hard error — a language invariant.
- No warnings anywhere: the diagnostic model has no severity field; every diagnostic is an
  error; no valid-with-warnings outcome exists.
- Multi-file discovery collects per-file errors and fails loudly; no warn-and-skip.
- Migrations execute only in the CLI and in tool-generated boundary checkpoints — never in
  read paths, never receiver-side, never automatically.
- The write path never serializes a non-current format_version.
- Raw untagged `map[string]any` is not a validation input; tagged values only.

## Release notes

Single module rooted at this directory's go.mod, module path `github.com/smm-h/strictspec/go`.
The Go companion-tag question is CLOSED: rlsbl's monorepo release flow emits `{path}/v{version}`
tags alongside `{name}@v{version}`, proven live in strictcli (both `go-strictcli@v0.25.3` and
`go/v0.25.3` tag families exist). The batch-regeneration helper (regenerate + commit across
all consumer repos after a strictspec release) is a required deliverable. Safety model: per
consumer repo, ONLY the manifest-declared generated paths must be clean and unmodified — other
working-tree dirt (concurrent sessions' work) is irrelevant; the follow-up commit is scoped to
exactly those generated paths and is made via `rlsbl commit` (the Autogenerated-trailer flow is
rlsbl's, never reimplemented); the helper NEVER pushes.
rlsbl integration: the diff certificate is the required input to rlsbl's format_version
deploy gate (wired as an rlsbl external check, like the pgdesign build-freshness pattern).
