# Appendix: Options

An option is a setting a family tool governs for a repository: a choice from a
closed set of values the tool declares. Options are the only sanctioned way to
change a family tool's behavior for a repository. No tool offers another
switch, exemption list, ignore flag, or config key that changes one of its
checks, and no flag that sets an option may be saved per person or read from
an environment variable.

What is not an option: an open value (a number, name, path, or list), a
declaration of what the project is, a product's per-user preference, and a
fact about a single commit (such as the `Autogenerated: true` trailer marking a
tool-written commit).

## Where options live

A repository's options live in `.strictmetadata/options/`, one TOML document
per subject (for example `changelog.toml`, `docs.toml`). The directory's
`manifest.toml` names `strictspec` as its owner and is not a subject document;
every other `*.toml` file in the directory is one, read in file-name order.
A repository with no entries has no files; a missing directory means every
option is at its default.

## The entry document

Each subject document is validated by the built-in schema `options-entries`:

```toml
format_version = 1

[[entry]]
id = "rlsbl:changelog-coverage"
scope = "..."          # optional; present only if the option declares a scope kind
current = "off"
ideal = "on"
reason = "fork: upstream's history is not ours to describe; waiting for rlsbl to limit coverage to our own commits"
```

- `id` is `<tool>:<name>`, using the tool's own name for the option; the
  tool is the text before the first colon.
- `scope` narrows the entry to part of the repository. Only options whose
  declaration names a scope kind accept it; its meaning belongs to the tool.
- `current` is the value the repository runs today; `ideal` is the value it
  should run. Both must be values the option declares, except that `ideal` may
  be `non-existent`: the right value is one the tool does not offer yet.
- `reason` is mandatory and non-empty.
- An entry exists only when `current` or `ideal` differs from the option's
  default. An entry whose `current` and `ideal` are both the default value
  itself is refused as redundant (a value merely ranked equal to the default
  is a real deviation).
- One entry per `(id, scope)` across all of the repository's subject files.

## The option registry

Each tool ships a separate options registry, validated by the built-in schema
`options-registry`, declaring every option it offers:

```toml
format_version = 1

[[option]]
name = "changelog-coverage"
subject = "changelog"
values = "on > deferred > off"
default = "on"
scope = "none"          # or a scope kind the tool defines, such as "path"
description = "..."
```

- `values` ranks the allowed values strongest first, using only `>` (stronger
  than) and `=` (equal rank), each with one space on either side, for example
  `npm = pypi = jsr > none`. Value names are lowercase letters, digits, and
  hyphens; `non-existent` is reserved and never declared.
- The registry does not name its tool: a reader passes the tool's name when it
  validates its namespace. Every registry field is required.
- `default` is one of the declared values.
- `subject` names the one subject file every entry for this option lives in;
  it follows the value-name grammar and is never `manifest`.

## Ranking rules

- **Debt:** `current` ranks below `ideal`.
- **Settled:** `current` and `ideal` have equal rank.
- **Refused:** `current` ranks above `ideal`.
- **Waiting on the tool:** `ideal` is `non-existent`. Such entries sit outside
  the ranking: they are neither debt nor settled, and together they form the
  tool's backlog of values repositories need.

## Validation

- Every reader validates the shape of every entry through the built-in schema.
- Each tool judges only its own namespace (`<tool>:*`). It refuses an unknown
  option name, a value its declaration does not list, an entry filed in the
  wrong subject file (naming the right one), a scope on an option that takes
  none, a redundant entry, and a `current` ranked above `ideal`. It never
  judges another tool's entries, so a tool a repository does not use cannot
  block it.
- The ranking parser, the entry loader, and the per-namespace validator live
  in strictspec's runtime, identically in Go, Python, and TypeScript, so every
  tool applies the same rules. Each refusal is a catalogued error in the
  `OPTIONS` area of the error-code appendix. The TypeScript runtime parses
  document text; loading files from disk is offered in Go and Python.

## Writing entries

Anyone may add an entry, as long as it carries a reason. Each tool offers a
command that validates and writes an entry for its own options; hand edits are
accepted and validated on read.

## Reporting

strictcode reports, in its normal run, every entry in debt and every entry
waiting on a tool, across all tools' namespaces, with each entry's reason.

## Renaming an option

When an option moves to another tool or is renamed, a strictspec migration
rewrites its `id` in every entry.

## The upstream document

A fork declares its upstream in `.strictmetadata/upstream/upstream.toml`,
validated by the built-in schema `upstream` (every field required; a
repository that is not a fork has no such file):

```toml
format_version = 1
host = "github.com"
owner = "ncruces"
repo = "wasm2go"
branch = "main"
```
