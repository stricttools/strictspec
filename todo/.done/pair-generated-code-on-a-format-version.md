# Pair generated code on a format version, not on the runtime's release number

## Context

Generated validator modules carry a `GENERATED_BY` constant naming the
strictspec release that produced them. At import time the runtime compares
that string with its own version and raises `PairingError` unless the two
are equal character for character (`check_runtime_version` and
`require_runtime_version` in `python/src/strictspec/__init__.py`). The
docstring calls this the intended surfacing of skew under the
always-latest dependency rule: the remedy is regeneration, never pinning.

For a checkout on a development machine that is the right behavior. The
runtime is installed editable, a mismatch shows up at the next import, and
`strictspec gen` fixes it in seconds.

For code that has been published it is not. The rules of this ecosystem
forbid upper bounds on dependencies, so a consumer declares
`strictspec>=X` and a fresh install resolves whatever strictspec is newest.
The moment strictspec publishes any release, every consumer already on a
registry starts failing at import, and stays failing until that consumer
regenerates and re-releases. A wheel cannot regenerate itself.

This happened: a consumer published with a validator generated by 0.1.0,
strictspec 0.2.0 shipped the next day, and every registry install of that
consumer failed at import for weeks. The consumer's checkout had been
regenerated twice in the meantime; nothing about the failure told anyone
the published artifact was the one that needed a release. The releases
that broke it did not change what the generator emits.

## Problem

The pairing check conflates two different questions:

- Did the shape of generated code change, so that this module may be
  wrong against this runtime? That is what pairing exists to catch.
- Is the installed runtime the same release as the one that ran the
  generator? That is what the check measures.

Every release answers the second question with "no" even when the answer
to the first is "nothing changed". Combined with floor-only dependencies,
that turns each strictspec release into an outage for every published
consumer, in dependency order, until the whole chain is regenerated and
re-released.

## Decision

Pair on a generator-format version. This was chosen deliberately by the
owner from the three options below, after the outage above.

## Solutions considered

### Pair on a generator-format version (chosen)

strictspec declares a format version, separate from its release version,
that is bumped only when the shape of generated code changes: a new
emitted constant, a changed calling convention, a changed diagnostic code
set, a changed runtime API the generated module relies on. The generator
writes that format version into the module, and the runtime accepts any
module whose format version equals its own. The release version stays in
the module as information, not as a contract.

- Pros: releases that do not touch generated code break nobody; a real
  format change still forces regeneration, with the same remediation text;
  the always-latest rule keeps working for checkouts because a format bump
  surfaces the same way a release does today.
- Cons: one more number to maintain, and a discipline requirement that any
  change to emitted code bumps it. That discipline needs a test, not a
  convention: a conformance fixture that fails when the emitted shape
  changes without a format bump.

### Keep the exact match

- Pros: the simplest rule; no new concept.
- Cons: every strictspec release requires regenerating and re-releasing
  every consumer before registry installs work again; the outage above
  recurs on every release; consumers deep in a dependency chain are red
  for as long as the chain takes to re-release.

### Self-contained generated modules

Generated modules carry everything they need and import nothing from the
runtime, so there is nothing to pair; strictspec becomes a development-time
dependency only.

- Pros: removes the failure class entirely.
- Cons: changes what the generator emits in every language, changes how
  consumers declare their dependency, duplicates runtime code into every
  generated module, and makes runtime fixes reach consumers only through
  regeneration. A much larger change than the problem needs.

## Design points to settle while implementing

- Where the format version lives. One declared constant per runtime port,
  held in lockstep across the Python, Go and TypeScript ports by the
  cross-language conformance suite, the same way other cross-port facts
  are held.
- What the emitted module records. Both numbers: the format version as the
  contract and the release version as information, so a remediation message
  can still say which release generated the file.
- The remediation text. It should name the format mismatch and the
  regeneration command, as it does today.
- Backward compatibility is not a goal. Modules generated before the format
  version existed carry no format field; the runtime treats a missing field
  as a mismatch and says so. Consumers regenerate once. No dual reading of
  old and new modules.
- External tooling that reads the emitted release constant as a dependency
  floor should read the format version instead, or keep reading the release
  constant with the understanding that it is now informational. State which
  in the docs so no tool guesses.
- The bump discipline. A test in the conformance suite that snapshots the
  emitted shape for each port and fails when it changes without a format
  version change.

## Affected files

- `python/src/strictspec/__init__.py`: `Version`, `check_runtime_version`,
  `require_runtime_version`, and the remediation message.
- The Python generator and its templates, wherever the emitted module
  header and the `GENERATED_BY` constant are rendered.
- The Go and TypeScript ports: their runtime pairing check and their
  generator's emitted header.
- `spec/` and `conformance/`: the format version as a shared cross-port
  fact, and the emitted-shape snapshot test.
- `DESIGN.md` and the generated docs: the pairing contract as stated to
  consumers.

## Effort

Medium. The runtime change is small in each port; the work is the
conformance test that enforces the bump discipline and the documentation
of the contract, plus one regeneration in every consumer when the first
format-versioned release ships.
