# Baked-result sketch — what `strictspec gen` produces for the sourced enum

At `gen` time the toolchain resolves `selector = "sounds[].name"` against
`sounds.registry.json`, compares the result to the `baked` list in the schema (freshness gate),
and emits a plain closed enum with those arms inlined. The generated code contains NO reference
to the source document — the source→schema edge is resolved entirely at build time.

Resolved from the source at build time:

    sounds[].name = ["kick", "snare", "hat", "clap", "tom"]

Freshness check: resolved list == `baked` list (order-insensitive set equality). Match ⇒ proceed.
Mismatch ⇒ `STRICTSPEC_ENUMSRC_STALE` (hard error in `gen` AND `check`).

Baked enum, as if hand-written (Go target sketch, illustrative):

    // Code generated by strictspec. DO NOT EDIT.
    type Sound string
    const (
        SoundKick  Sound = "kick"
        SoundSnare Sound = "snare"
        SoundHat   Sound = "hat"
        SoundClap  Sound = "clap"
        SoundTom   Sound = "tom"
    )
    // membership check at $.hits[i].sound -> STRICTSPEC_TYPE_NOT_ENUM_MEMBER on miss

The runtime enum is indistinguishable from a literal `values = [...]` enum: same accepted set
(appendix-semantics 3.13/3.21), same `STRICTSPEC_TYPE_NOT_ENUM_MEMBER` diagnostic with
did-you-mean. The ONLY difference is the build-time provenance edge and its freshness gate.
